# Reed 5.0.0 breaking changes

Use this guide when upgrading `@kozmof/reed` from 4.x to 5.0.0.

## Selection after edits

- `INSERT`, `DELETE`, and `REPLACE` move the current selection with the text. For example, inserting three bytes at offset 10 moves a caret at offset 20 to 23. A caret at the insertion point moves after the inserted text. An insertion at either edge of a non-empty range stays outside the range. A range wholly inside replaced text collapses to a caret after the replacement.
- Keep passing pre-edit offsets at UTF-8 code-point boundaries in an edit action's inline `selection`, or omit it to use the current selection. Reed now moves that selection through the edit. Dispatch `SET_SELECTION` after the edit to set a custom final selection. If your app needs that custom selection after redo, apply it again after `REDO`.
- `APPLY_REMOTE` adjusts the local selection after each remote change. A caret at the insertion point stays before the remote text.
- `UNDO` restores the selection from before the first edit in the history entry. `REDO` restores the selection after the last edit in that entry. An entry can contain several edits when they coalesce. Remove any caret adjustment that assumes redo ends at the end of the redone text.

## Selection notifications and revisions

- `selection-change` also fires when edits, remote changes, undo, redo, chunk loads, or chunk evictions move the selection. Update handlers that assume the event always comes from `SET_SELECTION`.
- Dispatching `SET_SELECTION` with the current selection leaves both revisions unchanged and emits no event. To detect all selection changes, listen for `selection-change` or compare `prev.selection !== next.selection`. Use `selectionRevision` to detect explicit selection changes.
- Chunk loads shift selection offsets as bytes become resident. Eviction shifts offsets and collapses endpoints inside the evicted chunk to its former location. At an unloaded chunk boundary, a `SelectionRange` can have optional `anchorAfterChunk` and `headAfterChunk` placement keys. Keep these keys when copying ranges for later use. Compare just `anchor` and `head` when checking byte offsets alone.

## Chunk eviction and undo history

- Manual eviction can now be refused while undo or redo history points into a chunk. This includes history left on the redo stack after an undo. Check the result with `store.didEvict(prev, next, chunkIndex)`.
- The default `historyEvictionPolicy` is `"pin-bounded"`. When eviction discards history, Reed checks each stack in replay order. It drops the first entry that depends on the evicted chunk and all older entries on that stack, even if those older entries never touched the chunk. To allow this when you are over your chunk limit, dispatch `DocumentActions.evictChunk(chunkIndex, true)`. Set `historyEvictionPolicy: "drop"` to allow manual evictions to discard history by default, or choose `"pin"` to keep chunks held by history even under memory pressure. Edits and attention anchors can still prevent eviction.
- `ChunkManager` now dispatches `EVICT_CHUNKS`. It evicts candidates that preserve history first. Under the default policy, if it still needs to evict, it chooses the candidate that discards the fewest history entries at each step. If your app enforces its own limit, use `DocumentActions.evictChunks(candidates, maxLoaded)` for the same policy. Handle `EVICT_CHUNKS` in exhaustive action switches and compare revisions with `next.revision > prev.revision`, since one dispatch can evict multiple chunks.
- A manager can adopt and evict chunks already resident when it starts, including chunks restored from a checkpoint. On stores that report an open transaction, the manager waits for it to close before running an eviction pass.
- While `ensureLoadedMany` is pending, the manager protects its requested chunks from eviction, including chunks already loaded. The call waits for each fetch it depends on to finish or be canceled before reporting a failure. A later eviction pass can remove requested chunks after the call settles. Use `setActiveChunks` to protect chunks the app still needs.

## History events and types

- If an undo or redo entry can no longer be applied, Reed discards it and the remaining entries on that stack. The text stays the same. `history-drop` carries `undoDropped` and `redoDropped` counts. It also fires when eviction discards history or when `APPLY_REMOTE` or `HISTORY_CLEAR` clears a non-empty history. To keep undo and redo controls current, compare `prev.history !== next.history` in a store subscription. Ordinary edits can add undo entries or clear redo without emitting `history-change` or `history-drop`.
- When a listener or event handler dispatches another action, events for that action are delivered after the outer action's events. Read the event's state for the action it describes. A live snapshot can already reflect a later action. Reed reports dispatch cycles that exceed its delivery limits. Actions can still take effect when the limits suppress their events.
- `HistoryChange.position` is now a number paired with a required `afterChunk` placement key. To recover the resident offset, start with `position` in the document layout where the change applies. Add the original byte lengths of the loaded chunks whose indices are at or below `afterChunk`. The stored position can be negative. In a document without chunks, the key is `-1` and the position is the byte offset.
- `HistoryEntry.selectionBefore` and `selectionAfter` now use `HistorySelectionState`. Both endpoints are anchored positions with separate placement keys. Update fixtures that construct history or piece nodes. `HistoryState` requires `evictionPolicy`, and `AddPieceNode` requires `afterChunk`.
- A single delete or replace can record several changes when it spans different chunk placement keys. A replacement records the later runs as deletes before the `replace` change. Its `oldText` and `oldByteLength` cover only the first run. Read the full `HistoryEntry.changes` list to account for all removed text.
- A history change can carry exact `bytes`, and a replacement can also carry `oldBytes`. Use `byteLength` and `oldByteLength` for lengths. Decoding and re-encoding the strings can lose the original bytes.

## Text reads and byte order marks

- `query.getText`, `scan.getValue`, and `scan.getValueStream` strip a UTF-8 byte order mark at the start of the file and keep U+FEFF elsewhere. A read starting partway through the file can now return a leading U+FEFF. In chunk mode, a U+FEFF at resident offset zero is kept if a preceding chunk is unloaded.
- Rendering methods such as `rendering.getLineContent` and `attention.getTextForAttention` now keep the leading mark. Use `query.getContentText` when mapping text to character positions or rendering columns, since the line index counts U+FEFF. Strip a file-leading mark explicitly in copy or display code that expects it to be omitted.

## Store wrappers and schedulers

- Custom implementations of `ReconcilableDocumentStore` now need `isInTransaction()`. Forward it if your wrapper delegates to a Reed store. Add `getContentText` to custom `QueryApi` implementations and `isRestorableCheckpoint` to custom `CheckpointApi` implementations.
- If a custom scheduler throws while Reed schedules reconciliation after a commit, Reed reports the error through diagnostics. The committed change still takes effect. Check your logger for scheduler failures that your code previously caught from dispatch or transaction commit.

## Checkpoint compatibility

- Reed writes version 2 checkpoints. Reed 4.x expects version 1, so keep your original checkpoints if you need to roll back the library upgrade.
- Reed 5.0.0 restores versions 1 and 2. If you use an envelope guard before restoring, switch from `checkpoint.isCheckpoint` to `checkpoint.isRestorableCheckpoint` to accept both versions. Restore performs full validation.
- The `CheckpointEnvelope.version` type is now the literal `2`. Use `RestorableCheckpointEnvelope` for envelopes that may come from either version.
- Version 1 migration keeps the newest entries on each undo or redo stack that can be replayed. It drops the first entry that fails replay and all older entries on that stack. Version 2 restore reports `HISTORY_INVALID` when a parsed stack fails replay. A malformed entry can report another error, such as `MALFORMED` for an unknown change kind.
- If your app reads checkpoint JSON directly, use `checkpoint.isCheckpoint` to check for a version 2 envelope. If your app reads both formats, check `version` before interpreting the sections. `checkpoint.isRestorableCheckpoint` also accepts envelopes whose sections still use the version 1 layout. In version 2, selection tuples can include placement keys, add-piece tuples can include `afterChunk`, and history tuples can include anchored positions, placement keys, and base64 bytes. Set `historyEvictionPolicy` when creating a store from a checkpoint to override the stored policy. See the [checkpoint format](../../spec/11-checkpoint.md#3-format).
